# Goat Farm Access — Product Audit & Architecture Review

*A record of the product/design/engineering thinking behind this pass. Written as PM + product designer + senior FE + platform architect. Grounded in a full read of the live codebase and Supabase database.*

---

## 1. Current State (what exists)

**Stack.** Vite + React + TypeScript + Tailwind + shadcn/ui, Supabase (Postgres + Auth + RLS), React Router, TanStack Query. Deployed on Vercel with an SPA rewrite.

**Identity & access.** One account model. `AuthProvider` resolves session → role, org memberships, athlete links, and `hasFanProfile`. `RequireFan` gates the fan surface; a fan is any user with a `fan_profiles` row. Following is a real relationship (`athlete_follows`, states following/subscriber/vip/former/blocked). Saved is real (`saved_items`). All RLS-protected.

**Data.** 51 active athletes (2 real + 49 clearly-flagged demo, `metadata.demo=true`), 50 with ESPN headshots. Athletes carry position + league. Only 2 athletes have real published merch (22 products, 15 with images) — everything else is demo content. Public reads go through two safe views: `public_athletes` (now incl. `image_url`) and `public_athlete_products`.

**Surfaces.** Bottom/top 5-tab nav: Home, Discover, Access, Shop, You. Plus Following, Camps, Saved, Notifications, onboarding (`/welcome`), public athlete profile (`/a/:slug`), product detail (`/p/:id`). Feed/camps/stories are generated by a deterministic demo-content layer; products/athletes are real DB reads.

## 2. Strongest Parts (preserve)

- **The relationship model is right.** One fan, many athletes, follow≠subscribe, real FKs, RLS. This is the scalable backbone and should not be touched.
- **The public-view seam** (`public_athletes` / `public_athlete_products`) cleanly exposes only safe columns and lets fans read without loosening core-table RLS. Excellent pattern; extend it, don't bypass it.
- **`AthletePhoto` with gradient/initials fallback** — the single source of athlete imagery. Keep as the only place image logic lives.
- **Clear mock/real separation.** Demo content is pure functions in `demo-content.ts`; real data is in hooks. This is the thing that makes a backend swap cheap. Reinforce it.
- **Reusable card system** (FeedCard, AthleteCard, CampCard, ProductCard, badges). Good component hygiene; no bloated files.

## 3. UX Problems (this pass addresses)

1. **Home was a flat vertical feed.** No hierarchy, no "featured" moment, no reason for the eye to land. A fan following 20 athletes got an undifferentiated wall. → Rebuilt as a hierarchical, sectioned home (featured hero + horizontal modules + focused feed).
2. **Discover under-used the network.** With 51 athletes it should feel like Netflix/Spotify browsing, not a list. → Added shelf rows incl. position-based (QBs/Receivers/Defense), Access, Camps, New to Goat Farm; kept powerful search with filters.
3. **Content and commerce were disconnected.** A photoshoot never pointed at a product. → Content items now carry product references; "Shop the Look" surfaces on content and product detail links back to the athlete.
4. **Feed, notifications, and "new" indicators were three separate derivations.** Divergent logic = drift. → Unified them behind one event source (`feed-engine`), so a new drop lights the avatar ring, appears in the feed, and generates a notification from the same object.
5. **No sense of time/urgency.** Drops and camps had no countdown. → Added drop countdowns and camp registration windows (incl. Access-early state).
6. **Image robustness.** A dead ESPN URL would show a broken image. → `AthletePhoto` now falls back to gradient+initials on load error.
7. **No unread signal.** The bell never indicated anything new. → Unread count derived from a stored last-seen timestamp.

## 4. Architecture Risks (and mitigations)

- **N+1 / over-fetching at scale.** Discover fetched every athlete. At 500+ this is a bottleneck. → Introduced a **service layer** (`services.ts`) as the single Supabase seam with an explicit `limit`, so pagination/infinite-scroll and server-side ranking can drop in without touching components. Documented as the backend integration point.
- **Feed generated client-side.** Fine for demo; won't scale to real content volume. → The `feed-engine` exposes a single `buildFeed(context)` interface. When a real `feed_items` table + ranking service exists, only that function changes; every surface keeps working.
- **Mock logic leaking into components.** → All demo generation stays in `lib/ecosystem/demo-content.ts` and `feed-engine.ts`; components receive typed objects and never know if the source is mock or real.
- **Notifications/preferences in a JSON blob.** `fan_profiles.preferences.notif` is fine now but won't support server-side fan-out. → Kept, but documented that a real `notifications` + `domain_events` table is the eventual home (PREPARE FOR).

## 5. Missing Features (state after this pass)

- **Content detail / galleries** — added a content detail route with Shop-the-Look. (Real media galleries: mocked.)
- **Editorial voice ("From the Farm")** — added stories surface + detail. (Real CMS: mocked.)
- **Recommendations** — added "Because you follow…" athlete recommendations by position/league. (ML ranking: PREPARE FOR.)
- **Drop countdowns / urgency** — added.
- **Unread notifications** — added.
- Still missing by design (see Future): real payments/billing, push/email, real content CMS, real analytics/ranking.

## 6. New Ideas Added (beyond the brief)

- **One event source powering three surfaces** (feed + notifications + avatar "new" rings). The most important architectural idea here: everything a fan reacts to is a `FeedEvent`, and every surface is a projection of the same stream.
- **"Shop the Look" as a relationship, not a page.** Content references a product id; the module renders anywhere.
- **Recommendation seam** (`recommendAthletes`) — deterministic today (position/league affinity), swappable for real ranking later.
- **Continue Exploring** — turns a follow-graph into discovery, so the product gets more useful as you follow more (the north star, made literal).

## 7. Implementation (what changed in this pass)

- Added `lib/ecosystem/services.ts` — typed Supabase seam (athletes, products, single lookups) with limits.
- Added `lib/ecosystem/feed-engine.ts` — one builder for feed items, notifications, "new" athlete ids, countdowns; links real products into demo drops.
- Added `lib/ecosystem/recommend.ts` — athlete recommendations from the follow graph.
- Hardened `AthletePhoto` (onError → fallback).
- Rebuilt **Home** (featured + sectioned), upgraded **Discover** (shelves incl. positions, Access, Camps, New), enriched the **athlete profile** (sectioned Home tab + Shop-the-Look), added **content detail** and **editorial stories** surfaces, unified **Notifications** (unread + shared events), and added **recommendations**.
- Expanded the demo network to ~50 athletes with headshots to stress-test discovery.

## 8. Future (do NOT build yet)

**PREPARE FOR (architecture ready, feature not built):**
- Real `feed_items` + `domain_events` + `notifications` tables and server-side fan-out (swap `feed-engine`'s source).
- Membership billing / payments (Access is a free preview; state model already exists).
- Server-side discovery ranking + pagination (service layer already limits).
- Real content CMS + media galleries (content types + detail route exist).

**LATER (good ideas, not now):**
- Weekly personalized digest (email) — strong retention lever once email infra exists.
- Geography-aware "Camps near you."
- Fan → athlete DMs / Q&A submission.
- Loyalty / early-access streaks (tasteful, not gamified).
- Cross-athlete campaigns and collabs surfaced to fans.
- Search across products/camps/stories (search is athlete-first but structured to extend).

# Phase — Operations: Event Engine, Templates, Drop Lifecycle

**QA findings.** Live click-through isn't possible in the build sandbox (Supabase egress blocked), so QA was code + data level: verified the shared-object loop returns through the public views (content/events/plans), confirmed RLS gates gated content, and confirmed the athlete-approval path works for platform-admin/impersonation (a real separate athlete account would need org membership or an approval RPC — noted below). Edge cases handled in components: not-signed-in (locked teasers + Join CTAs), missing images (gradient/initials + `onError`), empty content/events/plans (empty states), and timestamp-derived states so no operator has to flip a switch at launch time.

**Notification architecture (now real).** `domain_events` is an append-only event log written by **database triggers** on `content_assets` (publish), `events` (announce/registration_open), `athlete_follows` (follow/subscribe), and `products` (approval + drop scheduling). RLS decides the audience: operators/org members read their whole org stream (activity log); fans read only events for athletes they follow, gated by `audience` vs their follow state, and only once `occurred_at <= now`. The fan notification center + bell read these real events (merged with demo content), filtered by per-athlete preferences, with unread via a stored last-seen. `occurred_at` supports scheduled visibility. **Push/email/SMS delivery + timed fan-out are the documented next step (needs pg_cron/edge worker); the in-app read model is real.**

**Template system.** `athlete_templates` holds configuration (modules, default plans, content categories, notification defaults) — not athlete data. `apply_athlete_template(athlete, template)` provisions default membership plans (only if none exist) and writes modules/config to the athlete, then the athlete stays editable. Seeded NFL / College / High School templates. Applied from the athlete profile ("Apply Template"); browsable at Admin → System → Templates.

**Drop lifecycle.** Products carry `approval_state` (none→pending→approved/rejected) + `access_date`/`public_date`/`drop_date`. Operator schedules dates and "Send for Approval" on the athlete's **Drops** tab; the athlete sees "Action Required" in their portal and Approves / Requests Changes (with a note the operator sees). Fan UI derives the state from timestamps everywhere via one `earlyAccess()` helper: upcoming → "Access members shop early / Get Access"; access window → "Your early access is open"; public → normal. A `drop.scheduled` event notifies followers; approval outcomes notify operators.

**Shared objects, enforced.** One `products`, `content_assets`, `events`, `membership_plans`, `athlete_follows` — every surface is a permissioned view. No `fan_*`/`athlete_*`/`admin_*` copies.

**Still mocked / future.** Real billing (Stripe), push/email/SMS + timed notification fan-out, a full product *create* wizard (columns + scheduling exist; creation still uses the existing admin product flow), product/drop templates (athlete templates exist; merch templates are PREPARE-FOR), a separate-athlete-account approval RPC, and multi-athlete campaign tools.

**Next 5.** (1) A tiny scheduled worker (pg_cron/edge) to fire `drop.early_access_open`/`public` + membership renewal events at their timestamps — turns the derived UI into true notifications. (2) A product *create* wizard on the Drops tab (blank→design→images→price→schedule) so the whole drop is born in one place. (3) A "Coming Soon" fan surface + operator "Launch Calendar" over the scheduled dates. (4) Real per-subscription media gating (definer RPC) so gated *media* — not just metadata — is server-enforced. (5) Only after the above: Stripe, to convert the mock subscribe into revenue — the state model, plans, and access gating are already in place, so billing is now a genuinely small addition.

# Phase — Commerce Architecture: Collections vs Drops, Design Templates, Q&A → Preferences

**Reconcile-first.** The DB already had most of the creative scaffolding (`collections`, `collection_products`, `collection_designs`, first-class `designs` with metadata, `mockups` with product/design/blank/athlete refs + shot_type + tags, `product_social_assets`, `content_assets` with a `media` jsonb + `visibility`, and a full `questionnaires`/`questions`/`options`/`responses`/`answers` system). This phase added only what was genuinely missing and wired the operator surfaces onto the shared objects — no duplicate tables.

**Collections ≠ Drops (the core clarification).** A **Collection** is the permanent creative container (designs + mockups + products + drops that belong together — e.g. *Mooney World*). A **Drop** is a release/campaign event that selects products from a collection and schedules them. New: `drops` (athlete, collection, name, campaign image, access/public dates, notify, approval_state) + `drop_products` join, so **one collection has many drops** and **a product participates in many drops without being duplicated**. A DB trigger emits `drop.scheduled` to followers when a drop goes scheduled/live, and approval outcomes to operators (same event engine as products). A `public_drops` view is ready for the fan "Coming Soon"/Launch Calendar (PREPARE-FOR).

**Operator navigation.** Athlete management is now Products / **Collections** / Drops / Content / Access / Events. Collections shows visual cards (designs·products·drops counts + hero) → the existing Collection detail, extended with **Products / Designs / Mockups / Drops** sections (mockups resolved via the collection's product/design ids since mockups have no direct FK). Global operator search was upgraded: athletes rank first, match on full name (so "Darnell Mooney" works), show `position · team`, and a typed **Pages** group; products/designs/orders follow.

**Content: two purposes, real media.** Added `content_purpose` (access | marketing | editorial | internal) + `content_format` to `content_assets`, and rebuilt `public_content` to exclude marketing/internal so those never reach fans. The composer now splits **Access** (fan-facing, visibility-gated, notifies fans) from **Marketing** (athlete-facing IG feed/story/reel/promo/graphic/post-kit — downloaded & shared by the athlete). Both support real uploads (hero + gallery) to a new public `content-media` bucket. Post-kit tables (`post_kits`/`post_kit_items`) are laid as foundation.

**Design Templates (reusable STYLE systems).** `design_templates` (style, tags, color/typography tendencies, sport compatibility, compatible product types, and an `attributes` weight vector) — distinct from `athlete_templates` (which provision plans/modules). Seeded 8 styles (Vintage Sports, Y2K, Collegiate, Minimal, Luxury Sports, Streetwear, Tour/Concert, Heritage). Applying a template to an athlete writes a **non-destructive instance** (`design_template_applications.instance`) — the template is never mutated.

**Q&A becomes data.** Added `attributes` weights to questionnaire questions/options, a `fan_user_id` link on responses, a derived `preference_profiles` table (one per athlete/fan, `profile` = attribute→0..1), and `apply_response_to_profile(response_id)` — a transparent RPC that sums selected-option attribute weights and normalizes them. The recommendation seam (`recommendDesignTemplates`) is a deterministic, **explainable** cosine match: every recommendation carries the attributes that drove it ("Because: vintage, bold, football") and a match %. No black box, no ML yet — but the data is shaped so smarter ranking can drop in.

**Still mocked / next.** A merch/product *create* wizard on Drops; a browsable Design Template *library* page + fan design-discovery (schema + matcher exist; fan questionnaire UI is next); post-kit builder UI; and the scheduled worker + Stripe from the prior phase. The through-line holds: **data reduces work** — templates seed creative, Q&A seeds recommendations, collections tame asset chaos, drops coordinate launches, one event stream drives every notification.
